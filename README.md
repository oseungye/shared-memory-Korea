# Shared Memory — 동북아 역사 공동 기억 프로젝트

> 누가 옳은가를 AI가 판정하는 것이 아니라, 서로 다른 역사 서술이 어떤 언어와 관점을 사용하고 있는지 분석하고,
> 사용자가 실제 자료와 다른 참여자의 표현을 살펴본 뒤 자신만의 공동 표현을 제안하도록 돕는다.

한국·일본·중국의 역사 서술을 나란히 놓고 텍스트 분석(NLP)으로 비교한 뒤, 참여자가 직접 '공동 표현'을 제안하고,
모인 제안을 다시 분석해 **공동 기억이 형성되는 과정**을 데이터로 보여주는 디지털 인문학 웹 플랫폼입니다.
서버 없이 GitHub Pages에서 동작하며, 참여 데이터는 Supabase에 저장됩니다.

> 본선 시연 준비·당일 점검: [docs/finals-demo-checklist.md](docs/finals-demo-checklist.md)

---

## 1. 프로젝트 목적과 문제의식

- 1592년의 같은 전쟁도 한국에서는 흔히 '임진왜란', 일본에서는 '文禄・慶長の役'(그 밖에 '朝鮮出兵'·'朝鮮侵略'), 중국에서는 '万历朝鲜战争'·'抗倭援朝' 등으로 부릅니다. 한 나라 안에서도 여러 명칭이 함께 쓰이며, 단어 선택에는 시선이 담깁니다.
- 역사 교육은 흔히 한 국가의 서술만 전달합니다. 이 프로젝트는 세 서술을 **같은 화면에서, 같은 방법으로** 분석해 차이와 공통점을 드러냅니다.
- 차이를 확인하는 데서 멈추지 않고, 참여자가 서로 다른 관점을 함께 담는 표현을 직접 써 보고, 그 표현들이 어떻게 모이는지 봅니다.
- 이 과정에서 사실(침략·강제 동원·피해 등)을 지우거나 약화시키는 "중립화"를 정답으로 제시하지 않습니다.

## 2. 프로젝트 흐름

```
한국·일본·중국 역사 서술 비교
  → NLP 분석 (핵심 키워드 · 공통/특징적 표현 · 유사도 · 서술 강조점)
  → 관련 사료 확인 (누가, 언제, 어떤 위치에서 쓴 기록인가)
  → 참여자 공동 표현 작성 (Guided Contribution, 실시간 표현 분석)
  → 공동 표현 NLP 분석 (어휘·개념 · 유사도 · 표현 프레이밍)
  → Shared Memory 형성 (표현군 · 공동 기억 지도 · 탐구 전/후 변화 · 공감)
```

## 3. 주요 기능

| 영역 | 기능 |
|---|---|
| 사건 | 임진왜란 · 한중일 문화 교류 · 조공 관계 · 근대화 과정 · 재일조선인 · 히로시마 원폭과 조선인 피해자 (6개) |
| 국가별 서술 | 세 국가 서술 카드, 핵심 키워드, 편집자 해설(사람이 작성), 사건 타임라인 |
| 탐구 전 한 문장 | 서술을 읽기 전에 지금 알고 있는 내용으로 한 문장을 적어 둠 (선택) |
| NLP 비교 분석 | TF-IDF 핵심 키워드, 세 국가 공통 표현, 두 국가만 공유하는 표현, 국가별 특징적 표현, 코사인·Jaccard 유사도와 단어별 기여도, 원문 근거 위치 강조, **서술 강조점 비교**, 근거 → **관련 사료** 연결 |
| 키워드 비교 | 표현 묶음별 국가별 등장 횟수 — **서술 원문에서 자동 계산** |
| 관련 사료 | 자료명·원문명·연도·1차/2차 구분·작성 주체·소장 기관·관점·설명·링크, 연결된 표현 → 원문 근거 |
| 공동 표현 작성 | STEP 1 핵심 요소 선택 → STEP 2 표현 방식 → STEP 3 참고 예시·문장 틀(+ **작성 언어** 선택: 한국어 / 中文 / 日本語 / English, 고르지 않으면 자동 감지) → STEP 4 이유 선택+자유 입력, **실시간 표현 분석 패널** |
| 공동 표현 목록 | 전체 / 한국어 / 中文 / 日本語 / English 필터, 선택 요소·표현 방식·이유, 탐구 전 문장, **공감**, 참고 번역 예시 |
| 공동 기억 지도 | 전체·언어별 제안 수, **Shared Memory Map**(SVG), 공동 표현군(대표 키워드·대표 제안·제안 목록), 국가별 서술 → 참여자 표현 재구성, 자주 쓰인 어휘·개념, 표현 프레이밍, 탐구 전/후 변화 집계, 공감과 표현군 비교 |
| Shared Archive | 상단 메뉴 ‘Shared Archive’. **공개에 동의한** 공동 표현을 사건별 카드(문장·닉네임·작성 언어·날짜)로 모아 보고, 기존 **공감** 기능으로 반응. 사건마다 ‘이 사건 직접 탐구하기’로 4단계 탐구에 연결. 댓글 없음 |

### 3-1. 첫 방문 온보딩과 참여자 통계 (2026-10)

디자인(한지 배경·먹색·글꼴·히어로·지도 SVG·카드·버튼)은 그대로 두고, 처음 온 사람이 **무엇을 하는 곳인지 · 무엇을 하면 되는지 · 얼마나 걸리는지**를 바로 알 수 있도록 문구와 안내만 추가했습니다.

| 항목 | 내용 |
|---|---|
| 첫 화면 | “당신은 이 역사를 어떻게 기억하고 있나요?”, **5분 역사 인식 조사 참여하기** 버튼, `약 5분 · 익명 · 로그인 없음`, 버튼 바로 아래 실제 참여자 수, 참여 4단계(연령대 선택 → 역사 하나 보기 → 내 생각 남기기 → 결과 확인). 첫 화면과 사건 선택 화면에서는 ‘탐구’·‘공동 표현’·‘NLP’ 같은 전문 용어를 쓰지 않고, 상세 화면 안에서는 기존 명칭을 유지합니다 |
| 상단 메뉴 | 프로젝트 소개 · 지금 참여하기 · Shared Memory 보기 (휴대폰: 소개 · 참여하기 · 결과 보기). ‘지금 참여하기’는 연령대를 아직 고르지 않았으면 참여 시작 영역부터 열고, ‘Shared Memory 보기’는 사건을 고르면 공동 기억 지도 탭을 바로 엽니다. ‘탐구 의의’ 페이지는 첫 화면 소개 카드 아래 링크로 옮겼습니다 |
| 참여자 수 | Supabase 집계 함수 `participation_summary()` 결과만 표시(하드코딩 없음). 집계 함수가 없거나 0명이면 문구를 숨깁니다 |
| 연령대 (익명) | 참여 버튼을 누르면 “Shared Memory 참여하기” 영역이 열리고 `10대 · 20대 · 30대 · 40대 · 50대 · 60대 이상 · 응답하지 않음` 중 하나를 버튼으로 고른 뒤 **다음 → 역사 선택**으로 넘어갑니다. 공동 표현 작성 폼에서도 바꿀 수 있습니다. → `age_group` |
| 학습 경험 | 사건을 연 뒤 “탐구 전 한 문장” 카드에서 “이 사건을 이전에 배워보거나 자세히 접한 적이 있나요?”(있다·없다·잘 모르겠다·응답하지 않음) → `prior_learning` |
| 탐구 진행 표시 | `사건 선택 → 처음 생각 → 서술 탐구 → 공동 표현 → 결과 확인`. 권장 흐름을 보여줄 뿐 탭 이동을 막지 않습니다. 각 단계를 누르면 해당 위치로 이동하고, “다음” 안내가 한 줄로 나옵니다 |
| 닉네임 | 선택 항목. 비워 두면 ‘익명’으로 저장합니다 |
| 세대별 필터 | 공동 기억 지도에 `전체 · 10대 … 60대 이상` 필터. 고른 연령대의 제안만 **기존 분석 함수(`analyzeExpressions`, `aggregateBeforeAfter`)에 그대로 넣어** 제안 수·주요 어휘·개념·프레임·표현군·대표 표현·서술 유사도·탐구 전/후 변화를 다시 계산합니다 |
| 세대별 표현 차이 | ‘전체’ 보기에 연령대별 참여자 수·많이 쓰인 개념·표현 프레임 비율·서술과의 평균 유사도를 나란히 보여주는 작은 표. 차이가 작으면 “차이가 크지 않았습니다”라고 그대로 표시합니다 |

**완료 참여자 기준** (`completed_flow = true`): 사건 선택 + 탐구 시작 기록(사건 상세 열기 또는 탐구 전 문장) + **국가별 서술 확인**(서술 카드가 화면의 상당 부분에 5초 이상 보임) + 공동 표현 제출. 단순 방문자는 참여자로 세지 않습니다. NLP·사료 탭 열람(`viewed_nlp`, `viewed_sources`)은 추가 분석용으로만 기록하며 완료 조건이 아닙니다. 클릭 로그는 남기지 않고 이 네 가지 milestone만 제출 시점에 함께 저장합니다.

**표본이 적은 집단**: 연령대별 참여자가 `MIN_GROUP_SIZE`(기본 5명, `generation-analysis.js`) 미만이면 세부 분석을 표시하지 않고 “표본이 적어 세부 분석을 표시하지 않습니다.”라고 보여줍니다. 이 제안들도 ‘전체’ 분석과 전체 참여자 수에는 포함됩니다. 표본 크기는 서버 집계(중복 제거된 참여자 수)와 제안 수 중 작은 값을 씁니다.

**개인정보**: 이름·연락처·생년월일·정확한 나이·학교명은 수집하지 않습니다. 연령대는 10년 단위 구간만, 학습 경험은 4개 선택지만 저장합니다. 화면 안내: “참여 내용은 익명으로 프로젝트 개선과 통계 분석에 활용됩니다. 이름·연락처·생년월일 등 개인정보는 수집하지 않습니다.”

**데이터 해석의 한계**
- **연령대별 표현 차이는 참여한 표본에서 관찰된 경향일 뿐, 해당 연령대 전체의 역사 인식을 대표하지 않습니다.**
- 참여자는 무작위 표본이 아닙니다(자발적 참여, 수업·지인 경로 등에 따라 치우칠 수 있음).
- “차이가 크지 않음”은 프레임 비율 차이 15%p 미만·서술 유사도 차이 0.05 미만일 때의 기술적 표현이며 통계적 유의성 검정이 아닙니다(`DIFF_THRESHOLDS`).
- 연령대·학습 경험은 자기 응답이며 검증하지 않습니다. 브라우저별 무작위 키 기준이라 다른 기기·브라우저에서 참여하면 다른 사람으로 세어질 수 있습니다.
- 이 SQL 이전에 저장된 제안은 참여자 키가 없어 제안 1건을 1명으로 추정해 셉니다.

### 3-2. 본선 배포 전 안정화 — 교육 UX · 사료 신뢰성 · 개인정보 (2026-10)

디자인(한지 배경·먹색·Noto 서체·지도 SVG·국가별 포인트 컬러·카드·버튼)과 기존 기능은 그대로 두고, **쉬운 결과 → 근거 → 자세한 분석** 순서로 보이도록 정리했습니다.

| 항목 | 내용 |
|---|---|
| 대표 사건 | 사건 목록을 **임진왜란 → 재일조선인 → 나머지** 순서로 배치(`eventsData` 배열 순서, id는 그대로). 두 카드에만 작은 “먼저 살펴보기” 표시(`featured`) |
| 탭 이름 | 학생이 할 일을 먼저, 기술 이름은 작게: 세 나라의 서술(국가별 서술) · 어떻게 다를까?(NLP 비교 분석) · 단어 빈도(키워드 비교) · 사료로 확인(관련 사료) · 내 한 문장 쓰기(공동 표현 작성) · 모두의 기억 보기(공동 기억 지도) |
| 한눈에 비교 | NLP 탭 맨 위에 ① 세 서술이 공통으로 쓰는 말 ② 서술마다 두드러지게 쓰는 말 ③ 근거 확인 방법을 표시. **모든 단어는 `eventNlp`(세 서술 텍스트의 실제 계산 결과)에서 가져오며 미리 적어 둔 값이 없습니다.** 단어를 누르면 원문 위치 강조 + 연결 사료. 기존 TF-IDF·특징 표현·코사인/Jaccard·기여 단어·강조점·근거는 “자세히 분석하기”에 그대로 |
| 일반화 방지 | 비교 영역마다 “프로젝트에서 선정·요약한 자료이며 각 국가의 모든 교과서나 역사 인식을 대표하지 않는다”는 안내. 편집자 해설(`feature`, `editorNotes`)은 “이 서술은 …”, “한국 측 서술: …”을 주어로 다시 씀. 국가 카드 이름 ‘대한민국’ → ‘한국 측 요약 서술’ |
| 서술의 출처 | 각 서술 카드 아래 “이 서술은 어떻게 작성했나요?” — 편집자 요약임을 밝히고, `sourceRefs`(출처를 확인한 자료만)로 대조할 자료를 연결. 확인된 자료가 없으면 “참고용 관점 요약”이라고 표시 |
| 사료 검증 단계 | `verification: verified / partial / unverified` (화면: 출처 확인 · 일부 확인 · 검토 전). “원문/기관에서 확인하기” 버튼은 **verified 자료에만** 표시 |
| 사료 카드 | 1차 화면: 자료명·언제·누가·왜 볼까?·관점 주의·연결된 표현 / “자세히 보기”: 원문명·자료 종류·소장·제공·설명·확인 근거. 출처 확인 자료부터 정렬 |
| 사료 유도 | 사료 탭에 “텍스트 분석 → 근거 추적 → 관점 확인” 흐름 표시. 한눈에 비교 아래 “관련 사료 1개 확인하기 →”, 내 한 문장 쓰기 위에 “근거 자료 하나를 확인해 볼까요?”(사료를 아직 안 본 경우만, 필수 아님) |
| 탐구 전 한 문장 | “먼저 지금 알고 있는 내용만으로 한 문장을 적어 주세요. 검색하거나 정답을 찾지 않아도 됩니다.” 건너뛰기·빈 저장은 **한 번만** 이유를 설명하고 다시 묻습니다(강제하지 않음) |
| 빈칸 검사 | 밑줄 3개 이상(문장 틀 사용 시 2개 이상, 전각 ＿ 포함)이 남거나 빈칸을 지우기만 한 경우(“이 사건은 로 시작되어,”) 제출을 막고 고칠 위치를 알려줌. 일반 문장의 밑줄 1개는 허용 (`findPlaceholderIssues`) |

### 3-3. 공용 기기 — 새 참여자로 시작 (2026-10)

교실 PC·태블릿처럼 한 기기를 여러 학생이 쓰면, 브라우저 저장소(localStorage)에 남은 앞 학생의 연령대·탐구 전 문장·학습 경험·진행 기록·참여자 키가 다음 학생에게 이어질 수 있었습니다.

| 항목 | 내용 |
|---|---|
| 누가 참여하나요? | 이 기기에 이전 참여 기록이 있으면 **참여를 시작하는 동작(참여하기 버튼·상단 메뉴·사건 카드·제출) 전에** “다른 학생입니다 · 새 참여자로 시작 / 같은 학생입니다 · 이어서 참여하기”를 고르게 합니다. 선택은 이 창(탭)에만 기억합니다(새로고침해도 유지, 새 창은 다시 물음). **제출에 성공한 뒤**와 **15분 동안 조작이 없을 때**는 다음 참여 시작 때 다시 묻습니다 → 다음 학생이 일반 참여 버튼을 눌러도 앞 학생의 상태를 이어받지 않습니다 |
| 제출 직전 안전장치 | 선택하지 않은 채로 제출하면 저장 전에 같은 선택 창을 띄웁니다. 이때 “새 참여자”를 고르면 **지금 쓰던 문장·이유는 남기고** 이전 참여자의 연령대·탐구 전 문장·참여자 키만 지운 뒤 다시 등록하게 합니다 |
| 새 참여자로 시작 | 선택 창 외에도 첫 화면·사건 선택 화면(이전 기록이 있을 때만), 진행 표시 아래, 제출 완료 영역에 링크가 있습니다. Shared Memory 키(`sm_` 접두어)만 지우고 연령대 선택부터 다시 시작합니다 (`SharedStore.resetParticipant`) |
| 지우는 것 | `sm_age_group`, `sm_before_*`(탐구 전 문장·건너뛰기·학습 경험·제출 표시), `sm_flow_*`, `sm_participant_key`, `sm_voter_key`, `sm_empathized` + 화면의 입력창·작성 가이드·작성 언어 선택 등 메모리 상태 |
| 지우지 않는 것 | 같은 주소(GitHub Pages)의 다른 사이트 저장소, **데이터베이스에 이미 등록된 제안**(삭제·수정 요청을 보내지 않음) |
| 작성 중 확인 | 작성 중인 문장·이유·제출하지 않은 탐구 전 문장이 있으면 지우기 전에 확인 창을 띄웁니다 (선택 창에서 “새 참여자”를 골라도 동일). 선택 창은 Esc로 닫을 수 있으며 닫으면 아무것도 바뀌지 않습니다 |
| 제출 후 정리 | 제출에 **성공**하면 그 사건의 탐구 전 문장을 이 기기에서 지우고 “제출됨”만 표시합니다. 실패하면 문장과 입력 내용이 그대로 남습니다 |
| 같은 학생이 계속 | 버튼을 누르지 않으면 아무것도 지우지 않습니다(새로고침해도 유지) |
| 저장소를 쓸 수 없을 때 | 사생활 보호 모드·차단 등으로 localStorage를 못 쓰면 페이지가 열려 있는 동안 메모리에 보관합니다(오류 없이 참여 가능) |

브라우저 E2E — `tests/e2e/shared-device.e2e.js` (가짜 Supabase, 실제 DB 접속 없음): 학생 A 제출 → 같은 창에서 일반 참여 버튼 → 선택 창, 이어서 참여(키·연령대 유지), 15분 무조작 후 재확인, 새 참여자 B(연령대부터·탐구 전 문장·키 분리), 선택 없이 제출하는 C(문장 유지·정보 분리), 작성 중 삭제 방지, 제출 실패 보존, 저장소 차단 환경, 모바일.

**역사 용어 확인을 더 넓히지 않은 이유**: 국호·연대처럼 확실한 경우가 아니면 오탐(현재 시점 문장, 인용, 명칭 설명)이 커지고, 해석 판단으로 보일 위험이 있습니다. 그래서 임진왜란의 국호 한 가지만 두었습니다. 다른 사건(문화 교류·조공 등)은 기간이 길어 같은 규칙을 적용하면 정당한 문장까지 걸리므로 넣지 않았습니다.

### 3-4. QR 5분 탐구 · My Memory Card (2026-10)

QR코드로 들어와 약 5분 동안 한 사건을 탐구하고, **자신의 생각이 어떻게 움직였는지 담긴 개인 카드**를 받아 가는 흐름입니다. 기존 서술 비교·NLP·사료·공동 표현·공동 기억 지도는 그대로이며, 디자인(한지·먹색·서체·카드·버튼)도 유지했습니다.

| 항목 | 내용 |
|---|---|
| 사건별 링크 | `…/#/e/imjin` 처럼 사건 id를 붙이면 첫 화면 없이 그 사건이 바로 열립니다(`?e=imjin`도 지원). 해시 주소라 GitHub Pages에서 서버 설정 없이 동작하고, 없는 사건이면 첫 화면으로 갑니다. 사건 화면에 있는 동안 주소창에도 이 링크가 남습니다(`history.replaceState`, 뒤로 가기 기록을 늘리지 않음). 단, **새로고침**은 예전처럼 첫 화면에서 시작합니다(공용 기기에서 앞 사람이 보던 사건이 저절로 열리지 않도록) |

### 3-4-1. My Memory Card 아트 컬렉션 · 인스타 스토리 (2026-10)

참여를 마친 뒤 카드 화면 맨 위 **카드 디자인**에서 동아시아 전통 미술에서 영감을 받은 디자인을 고르고, **카드(4:5)** 또는 **인스타 스토리(9:16)** 형식으로 저장·공유합니다. 카드 내용(문장·발견·질문·도장)과 기존 기능은 그대로이며, 바뀌는 것은 모양뿐입니다.

| 디자인 | 색감 | 장식 (모두 코드로 직접 그린 창작 그림) |
|---|---|---|
| **고문서** (기본) | 한지색, 주묵 | 한지 섬유 질감, 선장(線裝) 제본 실, 괘선, 제첨 ‘共同記憶帖’, 붙인 쪽지, 인장 |
| 민화 화조도 | 살구빛 바탕, 석류 주홍, 연두 잎 | 겹꽃 가지 두 갈래, 앉은 새·나는 새 한 쌍, 또렷한 윤곽선 |
| 우키요에 | 붉은 보카시 하늘, 짙은 녹색 땅 | 판화 여백과 굵은 먹 테두리, 세로 제목 칸 ‘共同記憶’, 화면을 가로지르는 매화 줄기 |
| 청록산수 | 석청·석록, 황토 | 비단 결, 겹친 봉우리(준법·태점), 구름, 소나무, 물결 |
| 기본 | 이전 디자인 | 한지색 + 이중 테두리 + 세 나라 색 띠 |

- **문장이 주인공**: 장식은 위·아래 띠와 가장자리에만 두고, 문장은 무늬 없는 종이 패널 위에 둡니다. 패널을 넘어오는 장식은 글자 영역 밖으로 잘라 그려 문장을 가리지 않습니다. 모든 테마에서 종이 위 본문 대비 7:1 이상, 작은 글자·강조색 4.5:1 이상(WCAG AA)을 테스트로 확인합니다.
- **인스타 스토리(1080×1920)**: 별도 배치입니다. 사건 → 탐구 전(작게) → **탐구 후 한 문장(크게, 76px부터 들어가는 가장 큰 크기로 자동 조절)** → 새로 쓴 말 → 탐구 기록 도장 순서이며, 인스타그램 프로필(위 250px)·답장 칸(아래 320px)에 가려지는 곳에는 그림만 둡니다. 긴 문장은 탐구 전 문장 줄 수 → 새로 쓴 말 줄 수 순으로 자리를 양보하고, 그래도 넘치면 “(긴 문장은 일부 생략)”을 표시합니다. 발견한 관점·남은 질문은 4:5 카드에만 담습니다.
- **미리보기 = 저장 이미지**: 화면 카드는 HTML 글자 뒤·앞에 같은 그림 함수(`card-themes.js`)로 캔버스를 깔고, 저장 이미지는 `drawCard`가 같은 함수로 그립니다. 스토리 미리보기는 저장될 이미지를 그대로 그립니다. 그림은 사건·테마별 시드로 고정되어 다시 그려도 같습니다.
- **공유**: 휴대폰에서 ‘인스타 스토리로 공유’ → Instagram → 스토리. 공유 기능이 없으면 이미지를 저장한 뒤 인스타그램에서 고릅니다. 파일 이름에 디자인과 형식이 붙습니다(`shared-memory-card-imjin-20261020-ukiyoe-story.png`).
- **개인정보**: 고른 디자인·형식도 저장소에 남기지 않고, ‘새 참여자로 시작’하면 기본값(고문서 · 4:5)으로 돌아갑니다.
- **접근성**: 디자인·형식 고르기는 라디오 묶음(화살표 키 이동)이고, 스토리 미리보기 캔버스에는 탐구 후 문장 전체를 담은 대체 텍스트가 있습니다.

**저작권 · 출처**
- 외부 그림·사진·텍스처 파일을 쓰지 않습니다. 모든 장식(가지·꽃·새·산·구름·인장·종이 질감)은 `card-themes.js`가 Canvas로 직접 그리는 **창작 벡터 그림**이며, 테스트(`tests/card-themes.test.js`)가 외부 이미지 참조가 없음을 확인합니다.
- 기획 단계의 참고 이미지(우타가와 히로시게 「명소에도백경 — 가메이도 매화 정원」(1857, 퍼블릭 도메인), 현대 민화 화조도, 청록산수 화첩, 한국 고문서 첩)는 **색감과 구성 관습**(보카시 하늘·세로 제목 칸, 짝지은 새와 꽃가지, 석청·석록 봉우리, 한지·인장·쪽지)만 참고했고, 구도·형태를 옮기거나 따라 그리지 않았습니다. 특히 현대 민화 작품은 저작권이 있을 수 있어 모티프 수준에서도 거리를 두었습니다.
- 카드 속 한자 문구(‘共同記憶帖’, ‘共同記憶’, 인장 글자)는 이 프로젝트를 위해 만든 문구입니다. 실제 작가의 낙관·서명을 흉내 내지 않습니다.
- 앞으로 실제 문화유산 이미지를 넣는다면 CC0 또는 공공누리 제1유형처럼 이용 조건이 명확한 것만 쓰고, 출처를 `sources-data.js`와 이 문서에 기록합니다.

**검증** — `tests/card-themes.test.js`(테마 5종·기본값, 대비, 스토리 안전 영역, 모든 테마 × 형식 × 최대 길이 그리기, 문장 전체가 패널 안에 그려지는지, 스토리 글자 크기 맞추기, 시드 고정, 외부 이미지 없음), `tests/e2e/memory-card.e2e.js`(디자인 고르기·화살표 키, 디자인을 바꿔도 문장 유지, 고른 디자인으로 PNG 저장, 스토리 미리보기·1080×1920 PNG, 가로 스크롤 없음, 새 참여자 초기화).

**남은 한계**
- 인스타그램 앱의 공유 시트 동작(스토리 바로 열기)은 기기·앱 버전에 따라 다릅니다. 실제 휴대폰에서 확인이 필요합니다.
- 화면 카드의 그림은 휴대폰 폭에서 작게 보입니다(저장 이미지는 1080px 기준으로 선명). 인쇄 시 그림은 화면에서 그린 크기를 늘려 씁니다.

### 3-4-2. 타이포그래피 — 동아시아 역사 아카이브 (2026-10)

전통 동아시아 서체의 결을 살리되 붓글씨·과한 장식은 쓰지 않고, 역사 전시관처럼 단정한 명조 + 현대적인 고딕 UI로 정리했습니다. 기존 레이아웃·색은 그대로입니다.

| 역할 | 서체 | 라이선스 · 공식 배포처 |
|---|---|---|
| 메인 타이틀 · 큰 제목 (`h1`, `h2`, 첫 화면·사건·페이지 제목) | **마루부리** Bold | SIL OFL 1.1 · 네이버 한글(hangeul.naver.com) 공식 웹폰트 서버 `hangeul.pstatic.net` |
| 메뉴 · 버튼 · 안내 · 본문 | **Pretendard** (가변) | SIL OFL 1.1 · 공식 GitHub `orioncactus/pretendard` v1.3.9 배포본(jsDelivr), 다이내믹 서브셋 |
| 카드 제목 · 서술 · 질문 | **Noto Serif KR** | SIL OFL 1.1 · Google Fonts |
| 참여자의 문장 (공동 표현 · 카드 인용) | **고운바탕** | SIL OFL 1.1 · Google Fonts (디자이너 류양희) |
| 일본어 (`lang="ja"`) | **Zen Old Mincho** | SIL OFL 1.1 · Google Fonts (디자이너 Yoshimichi Ohira) |
| 중국어 간체 (`lang="zh-Hans"`) | **Noto Serif SC** | SIL OFL 1.1 · Google Fonts |
| 영문 라벨 · 연도 | Cormorant Garamond (기존) | SIL OFL 1.1 · Google Fonts |

**LXGW WenKai(霞鹜文楷)를 쓰지 않은 이유** — 라이선스(OFL 1.1)는 문제가 없지만, Google Fonts에는 번체판(LXGW WenKai TC, `chinese-traditional`)만 있습니다. 이 프로젝트의 중국어 콘텐츠는 간체(사건 이름 ‘万历朝鲜战争’, AI 답변, 참여자 문장)라 번체판으로는 일부 글자가 다른 서체로 섞여 보일 수 있습니다. 간체 웹폰트는 공식 경로가 아닌 개인 패키지로만 배포됩니다. 또 해서(楷書) 계열이라 ‘붓글씨 지양’ 방향과도 맞지 않아, 같은 명조 계열인 Noto Serif SC를 썼습니다.

**정리한 것**
- `style.css` 맨 위 `:root`에 서체 역할(`--font-display/serif/quote/ui/latin/ja/zh`), 글자 크기 7단계(`--fs-2xs` 12px ~ `--fs-xl` 18px), 행간(`--lh-*`), 자간(`--ls-*`) 변수를 두었습니다. 흩어진 크기 25종 311곳, 자간 29곳, 행간 63곳을 이 단계로 옮겼고, 가장 작은 글자를 10–11.5px에서 12px로 올렸습니다(모바일 가독성). 큰 제목(1.2rem 이상)은 기존 값을 유지했습니다.
- 사건 이름(일·중), 공동 표현, 표현군 대표 문장에 `lang` 속성을 붙여 언어별 서체가 적용됩니다(기존 AI 답변 포함).
- **Memory Card 테마별 서체 조합** (`card-themes.js`의 `fonts`, 화면 카드와 저장 이미지가 같음)

  | 테마 | 제목 | 참여자 문장 | 장식 속 한자 |
  |---|---|---|---|
  | 고문서 | Noto Serif KR 700 | 고운바탕 | Noto Serif KR |
  | 민화 화조도 | 고운바탕 | 고운바탕 | Noto Serif KR |
  | 우키요에 | Noto Serif KR 900 (판화의 굵은 윤곽) | Noto Serif KR 700 | Zen Old Mincho (제목 칸 ‘共同記憶’) |
  | 청록산수 | Noto Serif KR 500 (문인화처럼 가볍게) | 고운바탕 | Noto Serif SC (인장) |
  | 기본 | Noto Serif KR 700 | Noto Serif KR 700 | Noto Serif KR |

  안내·라벨은 Pretendard, 영문 라벨은 Cormorant Garamond로 모든 테마에 공통입니다.

**이미지 저장 시 서체** — 이전에는 `document.fonts.load()`에 글자를 넘기지 않았습니다. Google Fonts·Pretendard는 글자 범위별로 파일이 나뉘어 있어, 이렇게 하면 영문 조각만 내려받고 한글·한자 조각은 빠질 수 있었습니다. 특히 화면 카드가 숨겨지는 스토리 모드에서는 이미지가 기본 서체로 그려질 수 있었습니다. 이제 `MemoryCard.fontLoads(model, { theme, format })`가 테마 서체와 **실제로 그릴 글자**를 함께 넘기고, 다 받은 뒤(최대 3초) 그립니다.

**로딩 성능**
- 서체 CSS(Pretendard, Google Fonts)를 **비동기로 불러와 화면 그리기를 막지 않습니다**(`media="print"` → `onload`, JS가 꺼져 있으면 `<noscript>`). 학교망처럼 서체 CDN이 응답하지 않는 상황을 흉내 내 측정했더니, 첫 화면 표시가 이전(Google Fonts 1개가 화면을 막던 구조) **8.2초 → 0.3초**로 줄었습니다.
- 모든 서체는 `font-display: swap`입니다. 기본 서체로 먼저 보이고, 서체가 도착하면 바뀝니다.
- Noto Sans KR(4개 굵기)을 빼고 Pretendard 다이내믹 서브셋으로 바꿨습니다(쓰인 글자만 내려받음).
- Google Fonts는 글자 범위별로 나뉘어 있어, 일본어·중국어 서체는 그 언어 글자가 화면에 있을 때만 내려받습니다. 쓰지 않는 굵기는 내려받지 않습니다.
- 마루부리는 공식 웹폰트가 글자 범위로 나뉘어 있지 않은 한 벌 파일이라, 큰 제목용 **Bold 한 벌만** 불러옵니다. 첫 방문 시 내려받는 양이 가장 큰 서체이므로, 배포 후 실제 휴대폰 네트워크에서 확인하고 무겁다면 `font-display: optional`(두 번째 방문부터 적용)로 바꾸는 것을 권합니다.
- `preconnect`: fonts.googleapis.com, fonts.gstatic.com, cdn.jsdelivr.net, hangeul.pstatic.net

**검증** — `tests/card-themes.test.js`(테마별 서체 조합, 카드에 쓰는 서체·굵기를 페이지가 공식 배포처에서 모두 불러오는지, 저장 전 불러올 글자 목록, 캔버스가 테마 서체로 그리는지), `tests/e2e/memory-card.e2e.js`(저장 전 고운바탕·Noto Serif SC·Pretendard를 실제 문장 글자와 함께 요청), `tests/e2e/offline-vendor.e2e.js`(서체가 모두 차단돼도 기본 서체로 표시). 개발 환경에서는 외부 서체 서버에 접근할 수 없어, **실제 서체 모양은 배포된 사이트에서 확인이 필요**합니다(크기·간격·배치는 기본 서체로 확인).

**심사 대비 핵심 답변**

- **세 국가의 서술은 실제 교과서 원문인가?** 아닙니다. Shared Memory 편집자가 비교를 위해 쓴 짧은 요약 서술이며, 화면(서술 카드·소개 FAQ)과 이 문서에 그렇게 밝힙니다.
- **누가 작성했나?** 프로젝트 편집자(제작 학생)입니다. 편집자 해설(`feature`, `editorNotes`)도 사람이 쓴 해석이며 자동 분석과 구분해 표시합니다.
- **국가 전체의 입장을 대표하나?** 아닙니다. 예를 들어 일본에서도 임진왜란을 ‘朝鮮侵略’이라고 부르는 경우가 있어, 일본 측 요약은 ‘출병’ 표현을 쓰는 한 가지 서술 유형입니다.
- **출처는 무엇인가?** 서술마다 `sourceRefs`로 대조 자료를 연결하고, 자료마다 `verification`(출처 확인/일부 확인/검토 전)·확인 근거·확인일을 둡니다. 확인된 자료가 없는 서술(임진왜란 일본 측, 재일조선인 중국 측)은 화면에 “참고용 관점 요약”으로 표시합니다.
- **왜 이 사료를 선택했나?** 서술의 핵심 표현(침략·구원·외국인·특별영주자 등)을 당대 기록이나 법령 문장에서 직접 확인할 수 있는 자료를 골랐습니다(`whyRead`, `relatedTerms`).
- **사료마다 관점이 다른 것은 어떻게 처리했나?** 사료를 “정답”으로 쓰지 않고, 카드마다 작성 주체와 관점·한계(`perspective`)를 함께 적고 1차 사료/후대 편찬(2차)/기념물을 구분합니다. 예) 『명사』는 사건 약 150년 뒤 청 조정이 편찬한 2차 자료, 『징비록』은 당사자의 변호적 시각이 섞일 수 있는 회고록.

**아직 확인이 남은 것 (추가 확인 필요)**: 선조실록 개별 기사 URL, 징비록 원문 제공 페이지, 『조선일일기』(게이넨) 소장처·간행본, 일본·중국 고교 교과서의 실제 용어 사용(교과서별 원문 대조). 이번 점검 환경에서는 외부 사이트에 직접 접속하지 못해 기존에 확인한 URL은 검색 결과로 존재만 재확인했습니다.

### 3-6. 네 번째 서술자 · 기억의 빈자리 (2026-10, 본선)

세 나라의 서술처럼 **AI도 역사를 서술한다**는 관점에서, AI의 답을 정답이 아니라 비판적으로 읽을 ‘네 번째 서술자’로 다룹니다. 사건 화면 STEP 2의 탭 ‘AI는 어떻게 말할까?’(세 나라 서술 카드 아래 안내 버튼으로도 이동).

### 3-7. 기본 체험 — 객관식 관점 고르기 (2026-10)

학생이 사용법 설명 없이 3–5분 안에 끝낼 수 있도록, **임진왜란·재일조선인**의 기본 동선을 객관식 중심으로 줄였습니다. 기존 기능(탐구 전 문장·AI 네 번째 서술자·NLP·사료·자유서술 공동 표현·공동 기억 지도·Shared Archive)은 **심화 탐구**로 그대로 남아 있고, 나머지 4개 사건은 기존 흐름 그대로입니다.

```
첫 화면 큰 사건 카드(임진왜란 / 재일조선인) ─▶ ① 세 나라 기록 비교 ─▶ ② 관점 고르기(질문 3개, 한 화면에 하나)
   ─▶ ③ 한 줄 소감(건너뛰기 가능) ─▶ ④ My Memory Card
```

| 항목 | 내용 |
|---|---|
| 어디로 들어오면 기본 체험인가 | 첫 화면 **큰 사건 카드**, **QR·사건 링크**(`#/e/imjin`, `#/e/zainichi`). 사건 목록(‘다른 사건 · 전체 탐구 둘러보기’)·‘Shared Memory 보기’로 들어오면 기존 심화 탐구 4단계입니다 |
| 첫 화면 | 두 사건을 큰 카드(48px 이상 터치 영역)로 배치, `3–5분 · 익명 · 로그인 없음 · 정답 없음`. 연령대는 묻지 않습니다(기존 ‘전체 탐구’ 경로에서만) |
| 한 화면에 하나 | 단계마다 질문 하나와 화면 아래 고정 **다음** 버튼 하나, 2단계부터 **이전** 버튼, 진행 표시 `STEP n/4`와 `질문 n/3`. 탭·탐구 전 문장 칸은 숨김(‘심화 탐구’ 링크로 열기) |
| 객관식은 퀴즈가 아님 | “정답은 없어요. 내가 가장 중요하다고 생각하는 것 하나”를 고릅니다. 고르지 않고 ‘다음’을 누르면 그 질문은 **건너뛴 것**으로 남고(막지 않음), 카드·저장에 넣지 않습니다 |
| 선택지 작성 원칙 (`choice-questions.js`) | 모두 사실에 맞는 “무엇을 중요하게 볼 것인가”의 차이이며, 사실을 부정하는 선택지는 없습니다. 선택지에 나라 이름을 붙여 학생을 편 가르지 않습니다. 각 선택지에 근거(`basis`: 서술·연표·이름의 실제 낱말)를 적어 두고 테스트가 그 낱말이 데이터에 있는지 확인합니다. 순서 효과를 줄이려고 **선택지 순서를 참여자마다 돌려서** 보여줍니다(같은 창에서는 고정) |

## 5. NLP 방법론

모든 결과는 입력 텍스트에서 매번 계산됩니다. 분석 결과·비율·군집 이름을 코드에 미리 적어 두지 않습니다.

### 5-1. 국가별 서술 분석 (`nlp-analyzer.js`)

- **토큰화**: 어절 분리 → 규칙 기반 조사·어미 제거(예: 일본군을→일본군, 희생되었다→희생) → 불용어 제거. 각 토큰은 원문 위치(offset)를 기억합니다.
- **TF-IDF**: `TF × IDF`, `IDF = ln((1+N)/(1+df)) + 1`. 말뭉치는 사이트의 전체 서술(6개 사건 × 3개국).
- **공통 표현**: 세 서술에 모두 나온 단어·2어절 표현. 두 국가만 공유하는 표현도 따로 표시.
- **특징적 표현 (distinctive expression)**: 평활화된 상대 빈도 비율, 정렬은 로그 오즈비 z-점수(Monroe et al. 2008 방식 간소화).
- **코사인 유사도**: TF-IDF 벡터 간 코사인. 공유 단어별 기여도의 합 = 코사인 값 (설명 가능성).
- **Jaccard 유사도**: 공통 어휘 수 ÷ 전체 어휘 수.
- **원문 근거**: 선택한 단어·개념이 원문 어디에 쓰였는지 강조.

### 5-2. 개념 사전 (`concept-lexicon.js`)

사람이 만든 다국어 개념 사전입니다. 예) `침략 · 침공 · 侵略 · invasion → invasion`.
26개 개념을 **갈등·책임 / 사실·기술 / 화해·협력** 세 가지 표현 프레임으로 나눕니다.
기계학습 모델이 아니며, 목록에 없는 동의어·문맥은 인식하지 못합니다.

### 5-3. 서술 강조점 비교 (`emphasisProfile`)

개념 사전의 한국어 표현이 각 국가 서술에 나온 횟수 ÷ 서술의 어휘 토큰 수(밀도)를 구하고,
세 서술 중 최댓값을 3으로 두어 ●(0~3단계)로 표시합니다. **편향 탐지가 아닙니다.** 덜 언급했다고 왜곡이라고 판단할 수 없으며, 부정문도 언급으로 셉니다.

### 5-4. 키워드 비교 차트 (`keywordGroupCounts`)

`events-data.js`의 `keywordGroups`에는 사람이 정한 "표현 묶음"(예: `'침략': ['침략', '침공']`)만 있고,
숫자는 각 서술(제목+본문)에서 실제 등장 횟수를 세어 만듭니다. 예전의 수동 입력 숫자(`keywordFreq`)는 삭제했습니다.

### 5-5. 참여자 공동 표현 분석 (`shared-memory-analyzer.js`)

**지원 언어**: 핵심 언어 한국어(`ko`) · 중국어(`zh`) · 일본어(`ja`), 추가 지원 영어(`en`). 화면 표시 순서는 한국어 · 中文 · 日本語 · English 입니다.
`unknown`은 언어를 판별할 수 없었던 기존 데이터 호환용으로만 남겨 두며, 언어 탭으로 따로 보여주지 않습니다(‘전체’에는 포함).

1. **작성 언어 결정**: 참여자가 STEP 3 아래에서 **작성 언어를 직접 고르면 그 값을 우선** 저장하고, 고르지 않으면 자동 감지 결과를 저장합니다 (`resolveLanguage`).
2. **언어 판별(자동 감지)**: 문자 체계 비율 — 한글이 있으면 `ko`, 가나가 있으면 `ja`, 라틴 문자가 주되면 `en`, **가나 없이 한자가 주되면 `zh` 후보**.
   - 일본어에도 가나 없이 한자만 쓴 짧은 표현(예: `朝鮮侵略`)이 있으므로, 한자 문장은 중국어 기능어·간체자(的·们·这·对·战·历 …) 같은 단서가 있을 때만 확정(`confident: true`)하고, 단서가 없으면 `zh`(확인 필요) + 후보 `['zh','ja']`로 둡니다. 일본 신자체(戦·歴·対 …)만 있으면 `ja` 후보입니다 (`detectLanguageDetail`).
   - 확정하지 못한 경우 작성 화면에 “자동 감지: 中文 (확인 필요)”를 보여 주고 작성 언어 선택을 권합니다. **자동 판별은 참고값일 뿐이며, 사용자 선택을 함께 쓰는 이유가 여기에 있습니다.**
3. **언어별 토큰화**
   - 한국어: 5-1과 같은 규칙 기반 조사·어미 제거
   - 중국어: **형태소 분석기가 아니라 규칙·문자 n-gram·개념 사전을 이용한 경량 분할**입니다. 한자 연속 구간 안에서 ① 개념 사전의 한자 표현과 상용어 목록에 최장 일치하는 부분을 먼저 단어로 떼고 ② 남은 부분은 기능어(的·了·是·在·和 …)를 경계로 나눕니다(단, `和平`·`对话`처럼 사전에 있는 단어 안의 기능어는 경계로 쓰지 않음). ③ 한 글자 조각(明·清·唐·宋 등 왕조명 제외)과 `我们`·`因为`·`可以` 같은 일반 기능 표현은 버려 과대평가를 막습니다.
   - 일본어: 한자·가타카나 연속 구간 (히라가나는 기능어로 보고 제외)
   - 영어: 불용어 제거 + 간단한 어미 정리
4. **특징 벡터**: `단어` + `문자 2-gram`(가중치 0.5) + `개념`(가중치 1.5)을 TF-IDF로 가중. IDF는 해당 사건의 공동 표현 + 국가별 서술에서 계산.
   - 문자 2-gram 덕분에 "국제전쟁"과 "국제적인 전쟁"이 겹치고,
   - 중국어는 단어 경계가 불확실하므로 2-gram을 단어 단위가 아니라 **한자 구간 전체**에서 만들되, 기능어가 낀 2-gram(`的东` 등)은 제외합니다.
   - 개념 사전 덕분에 "일본의 침략", "日本侵略朝鲜", "日本の侵略", "Japanese invasion"이 같은 개념을 공유합니다.
   - 다국어 비교: 국가별 서술은 한국어이므로, 중국어·일본어·영어 표현은 주로 개념 특징을 통해 서술·한국어 표현과 연결됩니다.
5. **유사도**: 코사인 (0~1).
6. **표현군(군집화)**: 평균 연결(average-linkage) 병합 군집화. 평균 유사도가 가장 높은 두 묶음을 차례로 합치고 0.24 미만이면 멈춥니다. 무작위성이 없어 같은 데이터 → 같은 결과. 2건 이상인 묶음만 표현군으로 표시. 400건을 넘으면 앞 400건으로 묶은 뒤 나머지를 가장 가까운 묶음에 배정.
7. **표현군 설명**: 이름 = 절반 이상 제안에 나타난 개념(없으면 "군집 안 등장 제안 수 × IDF" 상위 어휘) → `‘국제·동아시아 · 전쟁’ 중심 표현군`처럼 자동 생성. 대표 제안 = 다른 제안들과 평균 유사도가 가장 높은 제안(medoid).
8. **지도 연결선**: 표현군 중심 벡터 간 코사인 ≥ 0.12.
9. **국가별 서술 ↔ 참여자 표현**: 참여자 주요 어휘가 세 서술 공통/일부 서술/서술에 없던 새 어휘 중 무엇인지, 반복 개념이 어느 서술에 있었는지, 참여자 제안과 각 서술의 평균 유사도.
10. **표현 프레이밍**: 개념 사전 기준 프레임별 어휘 수 (예전 "긍정/중립/부정 감정 분석"을 대체).
11. **탐구 전/후 비교**: 새롭게 등장·유지·사라진 어휘와 개념, 두 문장의 유사도, 국가별 서술과의 유사도 변화.
12. **작성 중 실시간 분석**: 작성 언어(직접 선택/자동 감지), 선택한 요소 포함 여부, 사건 주요 어휘 포함 여부, 길이, 국가별 서술·기존 제안과의 유사도, 프레임 어휘, 탐구 전 문장과의 비교.

### 5-6. 의미 유사도(문장 임베딩)에 대해

브라우저용 다국어 문장 임베딩(예: transformers.js + 다국어 MiniLM)을 검토했지만 **사용하지 않았습니다.**

- 모델 파일이 수십~수백 MB라 GitHub Pages 첫 화면 로딩이 크게 느려지고, 모바일 데이터 부담이 큽니다.
- 외부 임베딩 API는 키를 브라우저 코드에 노출해야 합니다.

대신 **TF-IDF + 문자 n-gram + 다국어 개념 사전 + 코사인**으로 "표현은 다르지만 뜻이 가까운" 문장의 일부를 잡아냅니다.
따라서 화면과 문서에서 이 분석을 "AI", "임베딩", "의미 분석"이라고 부르지 않고 "텍스트 유사도"라고 부릅니다.
`analyzeExpressions`는 특징 벡터를 만드는 부분이 분리되어 있어, 나중에 서버(Edge Function)에서 임베딩을 계산하는 방식으로 확장할 수 있습니다.

## 6. 설명 가능성

- 모든 키워드에 등장 횟수·IDF·점수를 함께 표시합니다.
- 코사인 유사도는 기여 단어와 기여도(합 = 코사인 값)를 보여줍니다.
- 단어·개념 칩을 누르면 원문 위치가 강조되고, 연결된 사료가 나옵니다.
- 표현군마다 대표 키워드의 등장 건수, 표현군 안 평균 유사도, 실제 제안 목록을 보여줍니다.
- 각 분석 영역에 "분석 방법과 한계"를 펼쳐 볼 수 있습니다.
- 사람이 쓴 해석(편집자 해설, 표현 특징)은 자동 분석 결과와 구분해 표시합니다.

## 7. 분석의 한계

- 형태소 분석기가 아닌 규칙 기반 처리라 일부 활용형이 남거나 잘릴 수 있습니다.
- **중국어 분석은 형태소 분석기가 아니라 규칙·문자 n-gram·개념 사전을 이용한 경량 분석**입니다. 사전에 없는 단어는 기능어 경계로만 나뉘어 여러 단어가 한 덩어리로 남을 수 있고(예: `人民带来`처럼), 기능어 글자가 실제 단어의 일부일 때 잘못 나뉠 수 있습니다. 문자 2-gram과 개념 특징이 이를 일부 보완합니다.
- 가나 없는 한자 문장의 언어 자동 판별은 확정할 수 없습니다(짧은 일본어 한자 표현 ↔ 중국어, 번체 중국어 ↔ 일본어 구자체). 그래서 작성 언어를 직접 고를 수 있게 했으며, 저장된 값을 자동으로 바꾸지 않습니다.
- 중국어와 일본어는 같은 한자가 다른 뜻으로 쓰이는 경우(예: 差別 — 일본어 ‘차별’, 중국어 ‘차이’ / 独自 — 일본어 ‘독자적’, 중국어 ‘혼자’)가 있어 개념 사전이 이를 구분하지 못합니다. 분명히 겹치는 경우(在日 ↔ 在日本)는 사전 표현을 좁혀 두었습니다.
- 개념 사전에 없는 동의어·비유·반어, 부정문("굴종이 아닌")은 구분하지 못합니다.
- 국가별 서술은 편집자가 요약한 짧은 텍스트이며, 각국 교과서·학계 전체를 대표하지 않습니다.
- 제안 수가 적으면 표현군이 불안정합니다. 가장 큰 표현군은 "많은 참여자가 비슷하게 쓴 방식"일 뿐 정답이 아닙니다.
- 공감 수는 참여자의 반응이며 역사적 정답의 순위가 아닙니다.
- 사료 21건 가운데 출처를 확인한 자료(`verified`)는 5건, 일부 확인(`partial`) 2건이며 나머지 14건은 검토 전입니다(2026-10-16 기준, 임진왜란·재일조선인 우선). 검토 전 자료는 화면에 그대로 표시됩니다.
- 재일조선인·히로시마의 **중국 측 서술**, 임진왜란의 **일본 측 서술**에는 아직 출처를 확인한 대조 자료가 없습니다. 화면에서 “참고용 관점 요약”으로 표시합니다.
- 국가별 서술의 연표 날짜 중 임진왜란은 당시 기록 기준 음력입니다.

| `sm_choice_insert_guard` 트리거 | 전체 등록이 1분에 600건 이상이면 멈춤(자동 도배 방지) |
| `choice_counts(p_event_key)` 함수 | 선택지별 수만 공개. 질문별 응답이 `sm_min_group_size()`(5) 미만이면 그 질문은 돌려주지 않음 |

### RLS와 보안

- 브라우저에는 **publishable(anon) 키만** 있습니다. `service_role` 키·비밀 키를 절대 코드에 넣지 마세요.
- **Claude Code 프로젝트 설정**(`.claude/settings.json`): Supabase 조회 도구(목록·스키마·advisor)만 자동 허용하고, `execute_sql`·`apply_migration` 등 데이터·스키마·배포를 바꿀 수 있는 도구는 `ask`로 두어 실행 전에 확인을 받습니다(`tests/claude-settings.test.js`가 검사). 이 설정은 이 저장소에서 Claude Code를 쓸 때만 적용되며, 사용자·전역 설정, 세션 권한 모드, Supabase 대시보드·다른 도구에서의 변경까지 막지는 않습니다.
- `shared_expressions`: 조회·등록만 허용, 수정·삭제 정책·권한 없음. 등록은 허용 컬럼·CHECK 제약 범위 안에서만.
- `expression_empathy`: 등록만 허용, 조회 정책 없음. 집계는 함수로만.
- 공감 중복 방지는 브라우저별 무작위 키 기준입니다. 저장소를 지우거나 다른 브라우저를 쓰면 다시 공감할 수 있습니다. 더 강하게 막으려면 Supabase 익명 로그인(Anonymous Sign-in) + `auth.uid()` 기준 UNIQUE를 권장합니다.
- 등록 빈도 제한: `2026-10-server-moderation.sql` 적용 후 같은 제안 5분 내 재등록·전체 1분 120건 이상 차단. 공감 빈도 제한은 없습니다.
